Сервис отвечает за:

* создание заказов по SKU;
* обработку оплаты через webhook;
* автоматическую выдачу цифрового товара;

### `digital_store_api`

Основной backend-сервис.
Отвечает за:
* создание заказов;
* получение заказов;
* обработку webhook оплаты;
* изменение состояния заказа;
* постановку задач на выдачу;
* reconciliation.

### `digital_store_consumer`

Фоновый worker.
Отвечает за:
* получение задач выдачи из RabbitMQ;
* взаимодействие с поставщиками;
* retry;
* fallback;
* обработку DLQ;
* recovery зависших заказов.

### `digital_store_payment_service`

Тестовый эмулятор платёжного сервиса.
Реального эквайринга нет.
Сервис используется для:
* имитации успешной оплаты;
* имитации неуспешной оплаты;
* отправки payment webhook в `digital_store_api`;
* воспроизведения повторных webhook;

Сервис позволяет воспроизводить сценарии с повторными и параллельными webhook. Отдельный автоматизированный concurrency-тест в проект не включён.

### `digital_store_provider_a`

Основной тестовый поставщик цифровых товаров.
Поддерживает:
* успешную выдачу;
* ошибки;
* timeout;
* настройку поведения для тестирования retry.

### `digital_store_provider_b`

Резервный тестовый поставщик.
Используется для проверки fallback-сценария, когда Provider A недоступен.

### `digital_store_postgres`

Основная реляционная БД и источник правды для бизнес-состояния.

### `digital_store_rabbitmq`

Брокер фоновых задач.
Используется для асинхронной выдачи, retry и DLQ.

### Тестовый сервис, эмулирующий платёжную систему.
`digital_store_payment_service`

Реального эквайринга нет. `payment_service` используется для отправки подтверждения или отказа по оплате через отдельный HTTP endpoint.

Основной сценарий:

```text id="pmtflow"
Client
  │
  │ create order
  ▼
digital_store_api
  │
  │ order = created
  │
  ▼
payment_service
  │
  │ POST /payment/pay/{order_id}
  │
  │ payment confirmation
  ▼
digital_store_api
  │
  │ payment webhook
  ▼
RabbitMQ
  │
  ▼
consumer
  │
  ▼
Provider A / Provider B
```

Для подтверждения оплаты используется отдельный endpoint payment service:

```http id="pmtendpoint"
POST /payment/pay/{order_id}
```

Endpoint принимает данные заказа и формирует payment webhook согласно контракту платёжной системы.

Пример:

```json id="pmtexample"
{
  "order_id": "ord46",
  "status": "paid"
}
```
Поддерживаются статусы:

```text
paid
failed
```

После этого `payment_service` отправляет в `digital_store_api` webhook:

```json id="pmthook"
{
  "event_id": "evt_a1b2c3",
  "order_id": "ord46",
  "status": "paid",
  "amount": 500,
  "currency": "RUB",
  "created_at": "2025-01-01T12:00:00Z"
}
```

Таким образом, подтверждение оплаты проходит через тот же HTTP-контракт, который предполагается для реальной платёжной системы.

### Проверка гонок

`payment_service` также используется для воспроизведения конкурентных сценариев.

Для одного заказа можно отправить несколько подтверждений оплаты параллельно:

```text id="race"
payment_service
    │
    ├── webhook #1 ──┐
    ├── webhook #2 ──┤
    ├── webhook #3 ──┤
    │      ...       ├──► digital_store_api
    └── webhook #50 ─┘
```

Это позволяет проверить основной инвариант системы:

```text id="invariant"
50 параллельных webhook
        ↓
1 факт оплаты
        ↓
1 задача выдачи
        ↓
1 выданный код
        ↓
delivered
```

Повторная доставка webhook с тем же `event_id` также не должна изменять состояние заказа.
Отдельный автоматизированный тест на 50 параллельных webhook в проект не включён; сценарий может быть воспроизведён через payment_service.


# Exactly-once выдача

Главное требование задания — даже при 50 параллельных webhook одного заказа товар должен быть выдан **ровно один раз**.

Сам webhook не выполняет выдачу синхронно.

После подтверждения оплаты создаётся задача на выдачу:

```text
payment webhook
       │
       ▼
   PostgreSQL
       │
       ▼
 delivery.issue
       │
       ▼
   consumer
       │
       ▼
 provider
```

## Защита от гонки

Перед началом выдачи consumer атомарно захватывает заказ.

Используется блокировка строки PostgreSQL:

```sql
SELECT ...
FROM orders
WHERE id = ...
FOR UPDATE SKIP LOCKED;
```

Таким образом, если несколько worker'ов одновременно получили одну и ту же задачу:

```text
worker 1 ──┐
worker 2 ──┤
worker 3 ──┤
worker 4 ──┤──► PostgreSQL
...        │
worker 50 ─┘
```

только один worker получает право выполнять выдачу.

Остальные не могут одновременно изменить состояние этого же заказа.

# Повторный webhook

Повторная обработка уже завершённого заказа ничего не меняет.

Это позволяет выполнять webhook безопасно при:

* retry платежной системы;
* сетевых сбоях;
* параллельной доставке webhook;
* повторной публикации сообщения в RabbitMQ.

# Поставщики

В проекте реализованы две тестовые заглушки:

```text
Provider A
Provider B
```

Обе поддерживают:

* успешную выдачу;
* `4xx/5xx`;
* искусственную задержку;
* timeout;
* повторный запрос с тем же `request_id`.


### Автоматическая выдача товара

После подтверждения оплаты API автоматически запускает процесс выдачи товара.

Последовательность:

```text
создание заказа
      │
      ▼
payment_service
      │
      │ подтверждение оплаты
      ▼
digital_store_api
      │
      │ order → paid
      ▼
очередь delivery.issue
      │
      ▼
consumer
      │
      │ автоматически вызывает
      ▼
POST /issue
      │
      ▼
Provider A
      │
      ├── success ───────► код привязан к заказу
      │
      ├── timeout/error ─► retry
      │
      └── failure ───────► fallback Provider B
```

То есть endpoint поставщика:

```http
POST /issue
```

**не вызывается вручную пользователем**. Он вызывается автоматически фоновым `consumer` после того, как `payment_service` подтвердил оплату заказа.

Для каждого заказа при выдаче формируется `request_id`. При повторной попытке после timeout используется **тот же `request_id`**, что позволяет поставщику вернуть ранее выданный код и избежать двойной выдачи.


Пример:

```json
{
  "request_id": "req_ord46-1",
  "sku": "GIFT-ROBLOX-800",
  "order_id": "ord46"
}
```

Успешный ответ:

```json
{
  "status": "ok",
  "request_id": "req_ord46-1",
  "code": "LFXC-TNCS-BPCD"
}
```

# Ключевое решение: timeout ≠ отказ

Это наиболее важная часть интеграции с поставщиком.

Рассмотрим ситуацию:

```text
Наш сервис                  Provider A

   POST /issue ───────────────►
                                │
                                │ код выдан
                                │
                                ▼
                              code
                                │
                         ответ потерян
                                X
                                │
   timeout ◄───────────────────┘
```

Наш сервис **не знает**, успел ли поставщик выдать код.

Поэтому timeout нельзя считать подтверждённым отказом.

---

# request_id

Для каждой попытки выдачи используется стабильный `request_id`.

Например:

```text
req-order123-1
```

Если запрос завершился timeout:

```text
request_id = req-order123-1
```

не меняется.

При повторе отправляется тот же идентификатор:

```text
POST /issue

{
  "request_id": "req-order123-1",
  ...
}
```

Поставщик хранит результат выдачи по `request_id`.

Поэтому:

```text
первый запрос
     │
     └── timeout

retry с тем же request_id
     │
     ▼
тот же самый code
```

а не новый код.

Это предотвращает двойную выдачу после timeout.

---

# Retry

Для временных ошибок используется повторная попытка. Количество попыток ограничено, после чего задача может быть перемещена в DLQ.
После исчерпания попыток задача не должна бесконечно выполняться в основном worker'е.

---

# Fallback A → B

Основной поставщик:

```text
Provider A
```

резервный:

```text
Provider B
```

При подтверждённой ошибке Provider A выполняется fallback:

```text
A
│
├── success ─────────────► delivered
│
└── error
     │
     ▼
     B
     │
     ├── success ────────► delivered
     │
     └── error ──────────► delivery_failed
```

При этом задача выдачи остаётся идемпотентной.

Fallback не должен создавать вторую выдачу уже полученного кода.

## Сверка состояния заказов

Для контроля согласованности оплаты и выдачи предусмотрен endpoint сверки заказов.
```http
GET /check
```
# Сверка

Проверяются как минимум два класса расхождений:

### Оплачен, но не выдан

```text
payment = paid
delivery != delivered
```

### Выдан, но не оплачен

```text
delivery = delivered
payment != paid
```

Первый случай является ожидаемым кандидатом на восстановление.

Второй требует отдельного контроля, так как означает потенциальную бизнес-ошибку.

Endpoint возвращает список заказов, находящихся в этих состояниях. Результат используется для контроля согласованности данных и последующего восстановления проблемных заказов.

```json
{
  "paid_not_delivered": [
    {
      "order_id": "ord11",
      "delivery_id": "683c4eb1-ad44-49b6-8963-98e5bc00e8ed",
      "order_status": "delivering",
      "delivery_status": "delivering"
    }
  ],
  "delivered_not_paid": []
}
```

# RabbitMQ

RabbitMQ используется для асинхронной обработки выдачи.

В проекте используются три очереди:

- `delivery.issue` — основная очередь задач на выдачу товара. После подтверждения оплаты задача попадает в эту очередь, после чего consumer автоматически вызывает `POST /issue` у провайдера.
- `delivery.retry` — очередь повторной обработки задач, для которых выдача завершилась временной ошибкой.
- `delivery.dlq` — Dead Letter Queue для задач, которые не удалось обработать после предусмотренных повторных попыток.


Общий поток:

```text
API
 │
 ▼
PostgreSQL
 │
 ▼
delivery.issue
 │
 ▼
Consumer
 │
 ├── success ───────► delivered
 │
 ├── retry ─────────► retry
 │
 └── permanent error► delivery.dlq
```

---

# DLQ

Если задача не может быть обработана после предусмотренных попыток, она помещается в:

```text
delivery.dlq
```

Это позволяет:

* не блокировать основную очередь;
* сохранить информацию о проблемной операции;
* отдельно обработать ошибку;
* выполнить анализ причин;
* безопасно восстановить заказ.

Для DLQ предусмотрен отдельный worker.

# Recovery worker

Отдельный recovery worker периодически ищет зависшие операции.

Например, если заказ слишком долго находится в:

```text
delivering
```

он рассматривается как потенциально зависший.

Recovery worker:

1. находит зависшие заказы;
2. безопасно захватывает их;
3. проверяет текущее состояние;
4. повторно ставит выдачу;
5. не повторяет уже успешно завершённую выдачу.

Это позволяет восстанавливаться после:

* падения consumer;
* перезапуска контейнера;
* потери сообщения;
* сетевого сбоя;
* timeout;
* временной недоступности поставщика.

---


# Пустой остаток

Отсутствие товара у поставщика не считается падением сервиса.

В этом случае заказ переводится в восстановимое состояние:

```text
out_of_stock
```

После пополнения остатка выдача может быть повторена.

При этом уже выданный ранее код не может быть выдан повторно.

---

# Каталог

В проекте используется реляционная модель каталога.

Товар идентифицируется по:

```text
sku
```

Цена и валюта фиксируются для заказа.
Базовая валюта каталога:

```text
RUB
```

Пересчёт валют для backend не выполняется.

---

# Пул тестовых ключей

Для автоматической выдачи используется пул тестовых ключей.

Ключ после назначения заказу не может быть назначен другому заказу.

Таким образом обеспечивается инвариант:

```text
one code → one order
```

Конкурентная выдача защищена транзакциями PostgreSQL.

# Наблюдаемость

В проекте предусмотрены структурированные логи для критичных операций:

* создание заказа;
* обработка оплаты;
* запуск выдачи;
* попытка обращения к поставщику;
* timeout;
* retry;
* fallback;
* успешная выдача;
* ошибка выдачи;
* recovery;
* DLQ.

Для корреляции операций используются идентификаторы заказа и операции выдачи.

## Итоги по этапам задания

### Этап 1. Ядро API — ОБЯЗАТЕЛЬНО

**Реализовано:**

- REST API для создания заказа по SKU.
- Получение заказа по `order_id`.
- Приём webhook от платёжного сервиса.
- Отдельный `payment_service` для имитации подтверждения оплаты.
- После подтверждения оплаты заказ переводится в статус `paid`.
- После оплаты автоматически создаётся задача на выдачу товара.
- Consumer получает задачу из очереди `delivery.issue` и автоматически вызывает `POST /issue` у поставщика.
- Полученный код сохраняется за заказом.
- Реализованы корректные переходы статусов заказа:
  - `created` → ожидание оплаты;
  - `paid` → оплата подтверждена;
  - `delivering` → выполняется выдача;
  - `delivered` → товар выдан;
  - `payment_failed` → оплата не прошла;
  - `out_of_stock` → временно отсутствует товар;
  - `delivery_failed` → ошибка выдачи.
- Данные о заказах, товарах, оплатах и выдаче хранятся в PostgreSQL.

### Этап 2. Exactly-once под гонками — ОБЯЗАТЕЛЬНО

**Реализовано:**

- Обработка повторных webhook по одному заказу является идемпотентной.
- Для событий оплаты используется уникальный `event_id`.
- Реализована защита от повторной выдачи при конкурентной обработке webhook.
- Обработка заказа защищена транзакцией и блокировкой строки в PostgreSQL.
- Для конкурентной обработки используется `SELECT ... FOR UPDATE SKIP LOCKED`.
- Один ключ товара не может быть выдан двум заказам.
- Повторная обработка одного заказа не создаёт вторую выдачу.


**Не реализовано:**

- Воспроизводимый отдельный тест на параллельность, требуемый заданием, пока отсутствует.

### Этап 3. Устойчивые интеграции с ловушкой таймаута — сильно желательно

**Реализовано:**

- Используются два поставщика-заглушки: Provider A и Provider B.
- Поставщики могут возвращать ошибки и имитировать таймауты.
- Для интеграции предусмотрена обработка ошибок и повторная попытка выдачи.
- Используется fallback между поставщиками: при недоступности Provider A обработка может быть передана Provider B.
- Для каждой попытки выдачи используется стабильный `request_id`.
- Таймаут не рассматривается как гарантированный отказ поставщика.
- При повторной попытке после таймаута используется тот же `request_id`.
- Благодаря идемпотентности поставщика повторный запрос не приводит к выдаче второго кода, если первый запрос уже успел выдать товар.
- Для повторной обработки используются очереди `delivery.retry` и `delivery.dlq`.

> **Важно:** exponential backoff в текущей реализации не заявляется.

### Этап 4. Сверка, наблюдаемость, восстановление — бонус

**Реализовано:**

- Структурированные логи операций оплаты и выдачи.
- Endpoint `GET /check` для сверки состояния заказов.
- Проверяются расхождения:
  - «оплачен, но не выдан»;
  - «выдан, но не оплачен».
- Реализован фоновый recovery worker для обработки зависших заказов.
- Recovery worker периодически проверяет зависшие операции и безопасно возвращает их в обработку.
- Для фоновой обработки используются три очереди:
  - `delivery.issue` — основная очередь выдачи;
  - `delivery.retry` — повторная обработка;
  - `delivery.dlq` — окончательно неуспешные задачи.
- Повторная обработка не должна приводить к повторной выдаче уже выданного товара.

**Не реализовано:**

- Журнал денежных движений с контролем сходимости.

### Этап 5. Каталог под нагрузкой — бонус

- Каталог товаров хранится в PostgreSQL.
- Для поиска товара по SKU используется индекс.
- SKU является уникальным идентификатором товара в каталоге.
- Запрос получения товара по SKU не требует полного сканирования таблицы.
- Схема рассчитана на работу с большим количеством SKU.
- Для проверки производительности запроса может использоваться `EXPLAIN ANALYZE`.
- Основной запрос витрины остатков использует индекс по полю поиска, что позволяет сохранять предсказуемое время выполнения при росте количества товаров.
